Section 1

What this portal is

The University Admin portal is the operational control room for university leadership — the single place where a Vice-Chancellor, Registrar, or Dean can run the institution day-to-day.

Who uses it

Designated admin users at a university — Registrar, VC office, IT lead, Compliance officer.

What it controls

Programs, semesters, courses, users, admissions, AI models, credentials, compliance, budget, and reports.

How it’s structured

Six functional groups in the sidebar — Overview, Governance, Management, Intelligence, System — covering 21 pages.

In one sentence
The Admin portal is the place where the people running the university configure how the university actually runs — programs offered, when semesters happen, who teaches what, who attends, and how every action is governed and audited.

Section 3

Before the changes vs after

Here’s what changed at the platform level. The admin portal went from “polished UI but disconnected data” to “wired master data with safe-by-default flows”.

Platform-level changes

Before
  • Standalone Research portal cluttering navigation
  • Ministry & Research roles in role dropdowns
  • No master data — every form had hardcoded department lists, faculty IDs, semester options
  • Programs page didn’t exist
  • Semesters were a flat list with no hierarchy
  • Create User had a single “Name” field, no role-specific fields
  • Users table had no row actions
  • CSV import was a paste-into-textarea form
After
  • Research portal removed (deferred to Phase 2)
  • Role dropdowns show only the 4 active personas
  • Programs is the master — feeds Users, Courses, User Detail, Credentials
  • Programs page with full CRUD and impact-aware deactivation
  • Academic Calendar with hierarchical AY → Semesters
  • Create User form is role-first; fields adapt; First/Last separate
  • Action menu on every row (View / Edit / Suspend / Activate)
  • Drag & drop CSV uploader with row-by-row validation preview

Quality & integrity changes

Before
  • Counts were stored fields — drift the moment data changed
  • Course faculty was hardcoded fac_001..008 — broken when real backend hooked up
  • Eligibility checks didn’t exist — could enroll any student in any course
  • Suspending a user had no reason capture
  • Programs deactivate had no impact warning
  • AI Governance overview crashed on load
  • AI Models page was read-only — no actions possible
  • Bias reports had no “Mark Reviewed” flow
  • Reports list required manual refresh
  • Audit Trail rows truncated long details with no expand
After
  • Counts derive on every read — always accurate
  • Course faculty pulls from real Faculty users, live
  • Backend rejects ineligible enrollments (department mismatch) with a clear error
  • Suspend requires a 10+ char reason — logged in audit trail
  • Deactivate dialog shows live student count: “202 students currently enrolled”
  • AI Governance overview displays correct percentages (was 0.9% bug, now 88.7%)
  • AI Models support Trigger Retrain, Edit Owner, Deprecate / Reactivate
  • Bias reports support Mark Reviewed (with reviewer name) + Export CSV
  • Reports auto-refresh every 2s while any are generating; stops when done
  • Audit Trail rows expand to show full detail with copy-to-clipboard for IDs
Section 4

The 8 client commitments — line by line

These are the 8 items the client explicitly asked for in the call. For each one: the original ask (paraphrased), what we built, and why this is the correct interpretation.

1

Remove the Research portal

Scope cleanup Verified
“We won’t use the Research portal in the MVP. Remove it but keep the faculty’s research section.”

What we built: Removed research from the role enum, removed all /research/* routes and sidebar entries, removed the dev account. Faculty’s research sub-pages (Grants, Collaborations, Publications) are kept.

Why this is correct: The client wanted research as a separate portal gone, not research as a faculty capability. The role enum now reflects the 5 active personas (super_admin, student, faculty, admin, placement). Faculty research lives where it belongs — under the faculty role.

2

Clean up admin role dropdowns

UI cleanup Verified
“When admin creates a user, they shouldn’t be able to assign Ministry or Research.”

What we built: The Create User dialog, the User Detail page role-change dropdown, and the CSV bulk import schema all share one role enum: Student / Faculty / Admin / Placement.

Why this is correct: One source of truth across all three places where roles can be assigned — there is no path that lets an admin assign a deprecated role.

3

Export button on Users page

New feature Verified
“I want to export the users list as CSV.”

What we built: Export button next to Import and Create User. Generates a CSV with Name / Email / Role / Department / Status / Last Login / Created columns from the currently loaded data. Date is in the filename.

Why this is correct: The export reflects the active filter — admins get exactly what they see. Date in the filename keeps version history intuitive.

4

Role-first Create User form with dynamic fields

Form redesign Verified
“Right now the form asks for Name. We want First/Last separately. And the fields shown should adapt to the role.”

What we built: Role is the first select. Below it, sections render based on the selected role:

  • Student: Personal Info + Academic Info (Student ID, Program dropdown, Department auto-filled, Year Start/End, Current Semester capped at program’s totalSemesters)
  • Faculty: Personal Info + Professional Info (Employee ID, Department dropdown, Designation, Specialization)
  • Admin / Placement: Personal Info + Department only

Why this is correct: An admin never sees fields that don’t apply. Students must have a Student ID; Faculty must have an Employee ID. The form refuses to submit until role-required fields are filled.

5

Action menu on Users table

UX pattern Verified
“Each row should have actions — view, edit, suspend.”

What we built: Three-dot dropdown on each row: View Details / Edit / Suspend (or Activate if already suspended). Suspend opens a custom dialog requiring a 10+ char reason that’s written to the audit trail.

Why this is correct: Suspending a user cuts off their access. Capturing a reason is the minimum compliant pattern — auditors need to know why every suspension happened, not just that it did.

6

Drag & drop CSV uploader

UX pattern Verified
“The paste-into-textarea CSV form is awful.”

What we built: The FileUpload component is wired into Users → Import (for bulk user creation) and Courses → Enroll (for bulk student enrollment). Both have a Download Template button so the schema is obvious.

Why this is correct: The CSV is parsed and validated client-side before submit, so admins see row-by-row OK/error indicators and find typos before they hit the backend. The template removes guesswork.

7

Programs & Degrees master page

New page Verified
“We need a master data page for programs — duration, semesters, degree type. So when we add students, we just pick a program.”

What we built: New /admin/programs with full CRUD. Each program has name, department, duration (years), total semesters, degree type (UG/PG/PhD/Diploma). Search, filter, and a Deactivate flow that shows the live enrolled-student count.

Why this is correct: Programs is now the master that feeds three downstream forms — Create User auto-derives Department from selected Program, Course catalog department dropdown, and User Detail department edit. There is no place left where free-text typing creates phantom data.

8

Restructure Semesters → Academic Calendar

Restructure Verified
“Flat semester list doesn’t reflect how we plan. Academic year contains semesters. Auto-create Fall + Spring under it.”

What we built: Hierarchical Calendar at /admin/semesters. Each Academic Year is an expandable row containing its 2 semesters. Creating a year auto-generates Fall + Spring with date ranges derived from the year. Each semester is editable; end date < start date is rejected. Status (upcoming / active / completed) auto-derives from current date.

Why this is correct: Universities plan in academic years, not in flat lists of semesters. The new model matches reality. Auto-derived status means admins don’t have to flip statuses manually.

Section 7

Master data flow

Programs is the spine. Once it’s defined, it feeds everything that needs to know “what programs does this university offer?”

Master data hierarchy — Programs at the top, feeding every form that needs a department, program, or semester
Why master-data wiring matters
Before this engagement, every form had its own hardcoded list of departments, faculty, and semesters. That meant: (1) typos created phantom departments, (2) deleted faculty still appeared in dropdowns, (3) the dashboard showed counts that didn’t match the actual data. By making Programs the single source of truth, all of those problems disappear.

Section 9

Why this is correct — design principles applied

Each design decision can be defended on first principles. Here’s the reasoning.

Master data has one source of truth

Programs is the master. Every form that needs “what programs/departments exist?” reads from Programs, not from a hardcoded list. This prevents drift, typos, and orphaned references.

Principle Single Source of Truth

Counts are derived, never stored

studentCount, courseCount, enrolledCount are computed on every read. There is no stored value that can drift the moment underlying data changes.

Principle Derived state

Destructive actions warn with impact

Deactivate program shows live student count. Suspend user requires reason. Archive course shows enrolled count. Admins always see “what does this affect?” before they confirm.

Principle Safe-by-default

Backend enforces, frontend assists

Eligibility check, date validation, capacity limit, role enum — all enforced server-side. UI guides the user but cannot be bypassed by removing client-side validation.

Principle Defence in depth

Every action ends with feedback

Toast confirms success. Confirm dialogs prevent accidents. Errors are specific (“X is from Y, not Z” — not just “invalid”). No dead-end flows.

Principle No broken flows

Hierarchy matches mental model

Academic Year → Semesters reflects how universities plan. Programs → Departments → Courses reflects how curriculum is structured. The data model matches what admins already know.

Principle Match the domain
